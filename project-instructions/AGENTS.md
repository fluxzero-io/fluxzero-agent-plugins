# Fluxzero Agent Instructions

Use the installed Fluxzero plugin for all Fluxzero application work in this project. Retrieve current SDK guidance through `fluxzero-docs`, use `fluxzero-dev` as the exclusive owner of source watching, compilation, application processes, test selection, and test execution, and follow the `build-fluxzero-app` skill. Observe its structured results; do not manually rerun selected tests, existing regression tests, or the full suite after edits, and do not start duplicate builds, tests, applications, watchers, or log followers while that development environment is active. CI owns full regression coverage. A healthy compile/reload is sufficient when the Dev Server selects no tests. Make a new or changed test pass once through the managed loop, then let impact selection decide when it runs again. Only when verification is explicitly unmanaged may the agent run that new or changed focused test once itself. Keep one writer per feature slice; parallel agents must not edit the same files from stale snapshots.

Treat environment readiness as a hard gate before application work. Require working `git --version`, `fz version`, `fz mcp --help` with `--ensure-dev`, and `fz init --help` with `--in-place`; let the Fluxzero CLI own Java 25 detection. If Fluxzero reports that Java 25 is needed and the current execution environment permits software installation, install it yourself without asking the user, using `brew install openjdk@25` on macOS or Linux with Homebrew, or `winget install --exact --id EclipseAdoptium.Temurin.25.JDK --accept-package-agreements --accept-source-agreements --disable-interactivity` on Windows, then retry the original Fluxzero command. Treat existing agent execution permission as authorization. Only if the environment requires separate user approval, ask "Fluxzero needs Java 25. May I install it?" and continue after approval. Never ask the user to run commands, expose package, path, runtime, JDK, or environment-variable details in the permission question, or bypass denied permission. On macOS, inspect Apple Command Line Tools with `xcode-select -p` and `pkgutil --pkg-info com.apple.pkg.CLTools_Executables` before invoking Git. When both are absent, explain that this first Fluxzero build needs a one-time tool setup for fast, reliable builds and tests; run `xcode-select --install` exactly once, tell the user to finish Apple's dialog, and stop. Resume the same bootstrap after the user returns. Never bypass missing Git with a branch ZIP or mutable source archive, and never claim readiness based only on a successful plugin command.

The `fluxzero-dev` MCP server requires the Fluxzero CLI on the coding-agent process's `PATH`. If `fz` is unavailable, install it with `brew install fluxzero-io/tap/fluxzero` on macOS or Linux with Homebrew, `winget install --exact --id Fluxzero.FluxzeroCLI` on Windows, or `curl -sSL https://github.com/fluxzero-io/fluxzero-cli/releases/latest/download/install.sh | sh -s -- --install-path` on Linux or another supported Unix environment. On a bare Mac, finish Command Line Tools first, follow the current Homebrew instructions at `https://brew.sh`, and apply its printed shell setup; do not use the Unix fallback as the macOS route. Verify the CLI from a clean login shell and ensure GUI-launched agents inherit its directory. If this requires a native reload or restart, tell the user the one exact action and stop until it is complete.

Use the effective Maven or Gradle model for the SDK version actually used by this project; never infer a version from these instructions. Use `fluxzero-docs` for current SDK concepts and APIs, comparing its advertised `sdkVersion` with the project version before applying version-sensitive guidance. A mismatch alone is not a reason to upgrade or downgrade: use the manuals under `.fluxzero/agents` from the matching SDK release for version-specific project guidance, and change the SDK only when requested or required by the task. Only when manuals are insufficient, inspect `https://github.com/fluxzero-io/fluxzero-sdk-java` at the matching release tag, never `main`, for version-specific conclusions.

The installed CLI is authoritative for its evolving capabilities and for the dev-server version selected by this project. Use `fz --help` for the current CLI surface, `fz dev --help` for current development actions and options, and `fz dev config` before creating or editing `.fluxzero/dev.yaml`. Inspect existing configuration first. Do not infer flags, YAML keys, defaults, or precedence from these instructions, memory, another project, or a copied example; command output wins when guidance differs.

If the skill or `fluxzero-docs` server is unavailable, follow the complete onboarding at `https://plugins.fluxzero.io` (source repository `fluxzero-io/fluxzero-agent-plugins`) using this coding agent's native plugin mechanism. Gemini CLI calls plugins extensions. After activation, require the skill, complete `docs_start`, and complete a `get_status` call through `fluxzero-dev`; configuration or tool registration alone is not readiness. The status call must work in an empty workspace and identify its intended root. Initialize such a root with `fz init --in-place`, retaining the pre-init status cursor so the same dev session observes project discovery and verification. If the installed package is not available in the current session, tell the user which one agent-native action is required and stop before changing Fluxzero code. Do not substitute direct wrapper builds or a separately started dev server for a missing plugin MCP surface.

Use the plugin/MCP guidance and SDK-versioned manuals synchronized by the Fluxzero CLI as the managed documentation sources. Do not add hand-maintained Fluxzero manuals or duplicate either Fluxzero MCP configuration in this project.
